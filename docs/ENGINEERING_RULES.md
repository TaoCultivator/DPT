# 工程开发红线

本文记录 DPT 项目的工程开发约束。涉及具体测量定义和回归数值时，还必须阅读 `MEASUREMENT_SPEC.md` 和 `REGRESSION_BASELINES.md`。

## 参数计算保护

- 参数数值的计算千万别改。
- 涉及提取、测量、积分、斜率、时间窗等计算逻辑时，除非用户明确要求，否则只允许改展示层、交互层或样式。
- 如果用户要求修改计算逻辑，必须先说明：
  - 本次改动影响哪些参数。
  - 可能破坏哪些样例、模块或历史口径。
  - 需要如何验证，尤其是否需要跑全量 TSS 验证。

## 提示与交互约束

- 不要擅自新增弹窗提示、悬浮提示（ToolTip）或一次性提示。
- 如确实需要新增提示，必须先说明用途并获得用户明确同意。
- UI 文案或交互调整不能改变参数定义、默认落点或计算窗口。

## 重要实现前说明

重要实现前必须简短列出：

- 本次改动影响范围。
- 可能破坏的模块。
- 验证方式。

重要实现包括但不限于：

- 架构、状态管理、数据模型、权限、依赖、路由、主要 UI 结构变更。
- 波形绘制、通道映射、表格展示、导出、报告写入。
- TSS 提取、脉冲识别、平台线、损耗窗口、Trr/Err、积分和斜率。

## 长期可维护性

- 不允许为了短期跑通而引入长期难维护的临时方案。
- 如必须临时处理，必须在代码或规范中标记 TODO，并说明原因、影响范围和后续移除条件。
- 为兼容其他工况需要加入分支时，优先按波形特征自适应，不要用会改变黄金样例的全局常数硬推。

## 文档一致性

- 所有大的涉及功能、信息架构、数据结构、权限模型或主要布局的调整，都要询问用户是否同步更新项目规范，并提出更新大纲。
- 定期检查当前项目实际功能、UI、数据模型、交互流程是否与规范一致。
- 发现不一致时，主动提醒用户选择：更新代码、更新文档，或记录偏差原因。
- 当代码实现与文档方案发生偏离时，必须说明偏离点、偏离原因、潜在影响。
